## Magi-17 / Loose vs Medium Architecture

- User expected loose entry/strategy to create more paper trades than medium. Investigation found loose works upstream but not through execution:
  - Recent strategy evals: `loose evaluated 409 / passed 34`; `medium evaluated 480 / passed 18`; `strict evaluated 191 / passed 0`.
  - Persisted primary execution: `medium detected 9 / waiting 7 / invalidated 2 / confirmed 0 / planned 0 / opened 0`; `loose detected 9 / waiting 5 / invalidated 4 / confirmed 0 / planned 0 / opened 0` in one snapshot, later loose detected `11` with more invalidations.
- Top lifecycle blocker for loose/medium difference: `price_chased_beyond_max_chase_distance`. Loose permits wider initial anchor/entry (`maxAnchorDistancePct` up to about `1.2%`) but later `max_chase_pct` remains `0.8%`, so loose candidates are admitted upstream and often eliminated downstream.
- Verdict given to user: this is an architectural consistency issue, not simple tuning. Current system behaves like `detection_profile = loose` but `execution_profile = medium`; loose is discovery-only unless downstream confirmation/chase also scales. Recommended explicit split: `detection_profile: strict|medium|loose` and `execution_profile: strict|medium|loose`, or clearly label current behavior as loose detection with medium execution.
